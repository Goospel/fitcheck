# 데이터 보관·삭제·보안 정책

**E1·E2·E3 를 코드 대신 이 문서로 낸다.** 셋 다 배치 잡이라 3일짜리 시연에서는 **한 번도 안 돈다** — 만들어도 아무도 도는 것을 못 보고, 그 시간이면 F-10(사이즈 비교)이나 D6(중복 방지)가 죽는다 ([plan.md 8절](../plan.md)).

자른 것을 숨기지 않는다. **"설계는 끝났고 구현은 이후"** 가 이 문서다.

---

## 1. 지금 코드가 이미 하고 있는 것

아래는 계획이 아니라 **동작 중인 코드**다. 파일을 열면 그 자리에 있다.

### 비밀번호

| | |
|---|---|
| 저장 방식 | **bcrypt 해시** — 매 계정 랜덤 솔트 (`bcrypt.gensalt()`) |
| 평문 | **어디에도 안 남는다.** DB·로그·에러 응답 전부 |
| 검증 | `bcrypt.checkpw` — 해시를 되돌리지 않고 비교만 한다 |
| 출처 | `auth/security.py` |

bcrypt 는 솔트를 해시 문자열 안에 담으므로 **같은 비밀번호도 계정마다 다른 값**으로 저장된다. 한 계정이 뚫려도 다른 계정에 재사용할 수 없다.

### 전신 사진 — 이 서비스에서 가장 민감한 데이터

| | |
|---|---|
| 버킷 | **비공개.** 공개 URL 이 존재하지 않는다 |
| 접근 | **서명 URL 로만** — 유효기간 **1시간** (`SIGNED_URL_TTL = 3600`) |
| 재발급 | 조회할 때마다 새로 서명한다. 캡처해 둔 주소는 1시간 뒤 죽는다 |
| 저장 경로 | **서버가 정한다.** 요청에 경로를 실을 자리가 없다 |
| 출처 | `images/storage.py` · `api/photos.py` |

⚠️ **경로를 클라이언트에게서 받지 않는 것이 핵심이다.** 받으면 남의 전신 사진 경로를 자기 행에 적을 수 있고, 조회할 때 **서명 URL 이 정상적으로 발급된다.** 경로는 사용자 id 로 시작하게 서버가 만든다.

### 촬영 위치(GPS)는 저장 전에 떨어진다

폰 사진에는 EXIF 에 **찍은 장소의 좌표**가 들어 있다. 전신 사진과 같이 보관되면 그건 곧 **「이 사람이 어디 사는지」**다.

업로드된 사진은 회전을 픽셀에 굽고 **다시 인코딩해서** 저장한다 (`images/validate.py`). 이때 EXIF 가 통째로 떨어진다 — **덤이 아니라 지켜야 할 성질**이라 테스트로 못 박아 뒀다 (`tests/test_photo.py`).

### 부적절한 사진은 저장 자체를 안 한다

전신 사진은 업로드 시점에 비전 모델이 **사람이 있는지 · 전신인지 · 부적절하지 않은지**를 보고, 아니면 400 으로 거절한다 (`images/vision.py`). **검증이 저장보다 먼저**라 거절된 사진은 저장소에 올라가지도 않는다.

### 계정을 지우면 전부 같이 지워진다

```
DELETE /auth/me   (비밀번호 재확인 필요)
        ↓
  Storage 의 그 사용자 폴더 전체 삭제   ← storage.remove_user_photos()
  app_user 행 삭제
        ↓ 외래키 ON DELETE CASCADE 5개
  profile · garment · fitting · image_job 이 같이 사라진다
```

⚠️ **사진을 사용자 폴더 바로 아래 평평하게 둔 것이 이 때문이다.** 폴더를 더 파면 삭제할 때 **빠뜨린 가지에 전신 사진이 남는다.** `list` 한 번으로 다 걷히는 구조를 유지한다.

출처: `api/auth.py` · `db/models.py` · `images/storage.py`

### 그 밖에

| | |
|---|---|
| 기본키 | 전부 **UUID**. 순차 정수면 소유권 검사를 한 번 빠뜨렸을 때 남의 id 를 **찍어서 맞힐 수 있다** |
| 남의 자원 조회 | 「없다」(404)로 답한다 — **존재 여부 자체를 흘리지 않는다** |
| Supabase Data API | **꺼 뒀다.** 켠 채로 두면 anon 키만으로 전 테이블이 공개 REST 에 열린다 |
| 이미지 생성 실패 사유 | 모델 응답 원문을 저장하지 않는다 (API 키가 섞여 나올 수 있다). 응답 스키마에는 `error` 필드 자체가 없다 |
| 생성 프롬프트 | 영어로 만들어 모델에만 보낸다. **사용자에게 노출하지 않는다** |

## 2. 정책으로 제출하는 것 — 구현하지 않았다

### E1 · 보관기간 자동삭제

일정 기간이 지난 데이터를 자동으로 지운다. **지금은 사용자가 직접 지우는 경로만 있다** (계정 삭제 · 사진 덮어쓰기).

> ⚠️ **보관 기간 숫자는 아직 이 문서에 못 적는다.** [plan.md 8절](../plan.md)이 「30일·90일」이라고만 적어 뒀고, **각각 무엇에 붙는 기간인지**가 PRD 확인 사항이다. 지어내지 않는다 ([CLAUDE.md 1절](../CLAUDE.md)).

### E2 · 이상 로그인 알림

평소와 다른 기기·위치에서 로그인하면 사용자에게 알린다.

**메일 발송 인프라가 없어서 막혀 있다.** C2(이메일 인증 코드)와 같은 이유다 — SES·SendGrid 를 붙이는 데 반나절이고, 시연에서는 한 번도 안 지나가는 경로다.

### E3 · 1년 미접속 계정 삭제

마지막 접속으로부터 1년이 지난 계정을 지운다. **`app_user` 에 마지막 접속 시각 컬럼이 아직 없다** — 이것만 추가하면 나머지는 E1 과 같은 배치다.

---

## 3. 구현한다면 — 새 인프라가 필요 없다

셋 다 **이미 있는 것으로 돌아간다.** 이게 「설계는 끝났다」의 실제 내용이다.

**① 큐가 이미 배치다.** `image_job` 테이블 + `FOR UPDATE SKIP LOCKED` 로 도는 워커가 이미 있다 (`jobs/worker.py`). 삭제 잡도 같은 테이블에 다른 종류로 넣으면 워커가 그대로 집어 간다 — **Celery 도 cron 도 안 붙인다.**

**② 삭제 함수가 이미 있다.** `storage.remove_user_photos()` 와 외래키 CASCADE 가 계정 삭제에서 이미 검증됐다. 보관기간 삭제는 **대상을 고르는 쿼리 하나**가 다르고 지우는 방법은 같다.

**③ 지울 대상을 고르는 기준이 이미 컬럼에 있다.** `fitting.created_at` · `image_job.finished_at` 이 이미 저장된다.

남는 것은 **E3 의 마지막 접속 시각 컬럼 하나**뿐이다. 공용 DB 라 `ALTER` 한 줄이고, 마이그레이션 도구를 안 쓰기로 한 것도 [plan.md 8절](../plan.md)에 있다.

**E2 만 성격이 다르다.** 이건 배치가 아니라 **메일 발송 인프라**가 필요해서, 위 셋과 달리 「있는 것으로 안 된다」.
