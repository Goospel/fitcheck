### ✅ Q1 · 기장 5단계 판정 기준 — 종결 (2026-08-20)

**결론 — 경계를 지어낼 필요가 없었다.** 문구 5종이 실제 인체 랜드마크를 그대로
부르고 있었고, 그 랜드마크의 **바닥 기준 높이**가 제8차 조사 항목에 그대로 있다.

```
경계 = 목뒤높이 − 랜드마크높이          (목뒤에서 아래로 몇 cm)
```

| 문구 | 랜드마크 | 사이즈코리아 항목 | 항목 코드 |
|---|---|---|---|
| 허리에 딱 떨어지는 | 허리선 | 허리높이 | `S-STa-H-[FL01-WS11]-DM` |
| 골반에 걸치는 | 엉덩뼈 위 | 엉덩위높이/Top-hip높이 | `S-STa-H-[FL01-HP31]-SM` |
| 엉덩이를 반쯤 덮는 | 엉덩이 최대둘레 | 엉덩이높이 | `S-STa-H-[FL01-HP40]-DM` |
| 엉덩이를 완전히 덮는 | 볼기고랑 | 볼기고랑높이/다리안쪽높이 | `S-STa-H-[FL01-UL01]-SM` |
| (기준점) | 뒤목중심 | 목뒤높이 | `S-STa-H-[FL01-NK03]-DM` |

**뽑은 값 (8차 · 20~24세 평균, cm)** — `fit/length.py` 의 `LANDMARKS` 가 유일한 출처다.

| | 목뒤 | 허리 | 엉덩위 | 엉덩이 | 볼기고랑 |
|---|---|---|---|---|---|
| 남성 (n=789) | 148.35 | 106.56 | 96.79 | 86.17 | 77.90 |
| 여성 (n=714) | 136.33 | 98.42 | 89.13 | 79.10 | 71.19 |

키로 스케일한다 (`키비 = 사용자키 / 앵커키`) — A4 와 같은 앵커(남 174.99 · 여 161.79)를
쓴다. **둘레에 쓰는 `체형비` 가 아니다** — 살이 쪄도 허리 위치는 안 내려간다.

밴드는 **하한 포함·상한 미포함** (핏 등급 0/6/14/24 와 같은 규칙).

#### 어젯밤에 「남은 결정」이라고 적어둔 것은 결정이 아니었다

**총장을 어디서부터 재는가** — HPS 기준이면 항목을 갈아 끼워야 한다고 썼는데, 두 가지가
틀려 있었다.

- **HPS 는 `어깨높이`(어깨점)가 아니라 `목옆높이`(목옆점)다.** 어깨점으로 오해하면 7cm 를
  갈아 끼우게 된다 — 밴드 폭에 맞먹어서 판정이 한 칸씩 밀린다
- **제대로 된 항목(목옆높이)으로 재면 차이가 0.67cm(남)·0.61cm(여)뿐이다.** "1~2cm"라고
  적은 어림이 우연히 맞았다. 밴드 폭 8~10cm 라 **판정을 못 바꾼다**

그래서 표본이 크고 직접측정인 **목뒤높이**(`-DM`, n=789/714)로 갔다. 목옆높이는 `-SM` 이라
표본이 절반(n=446/443)이다.

#### 남은 근사 하나 — 문서에만 있고 코드에는 0 이다

**총장은 평면 실측이고 랜드마크 높이는 수직 높이다.** 옷은 입으면 등 곡면을 타고
내려가므로 실제 도달점은 계산보다 **조금 위**다. 몇 cm인지는 실착 데이터가 없어
`fit/length.py` 의 `DRAPE_ALLOWANCE = 0.0` 으로 두었다 — 값 하나만 올리면 경계 4개가
같이 올라간다. **테스트가 이 값을 못 박고 있어** 조용히 바뀌지 않는다.

#### 덤으로 알게 된 것 — 기장에서는 성별이 거의 무의미하다

같은 키로 정규화하면 남녀 경계 차이가 **최대 0.9cm** 다 (밴드 폭 8~10cm). A4 의 둘레
추정과는 딴판이다. 「밝히지 않음」을 골라도 기장 판정은 사실상 안 흔들린다.

### Q2 · 소매 3단계를 무엇으로 판정하는가

**막는 것** 없음 — **A3 는 기장만 채우고 나갔다** (2026-08-20). `sleeveLabel` 은 계약대로
`null` 로 나가고, 프론트는 이미 `null` 분기를 갖고 있어야 해서 아무것도 안 깨진다.
정해지면 `fit/length.py` 옆에 같은 방식으로 붙이면 된다. · **승인 등급** 3명 동의 (확정 상수)

Q1과 같은 문제인데 훨씬 작다. 계산식은 이미 있다.

```
소매 길이 차 = 의류 소매길이 − 사용자 팔길이     ← CLAUDE.md 1절, 확정
손목 위 / 손목 / 손등 일부 덮음                  ← 문구도 확정
```

**모르는 것은 경계 2개뿐이다.** 몇 cm부터 "손목"이고 몇 cm부터 "손등 일부 덮음"인가.

**필요한 답** — 숫자 2개. 예: `−3cm 미만 = 손목 위 / −3 ~ +2 = 손목 / +2 초과 = 손등 일부 덮음` (숫자는 **예시일 뿐 확정 아님**)

### 🔎 절반은 근거가 있다 (2026-08-20 조사)

**「손목」의 위치는 이미 정해져 있다.** 사이즈코리아 `팔길이` 는 **어깨점에서 손목까지**라 A4 가 추정하는 사용자 팔길이가 곧 손목 지점이다. 즉 위쪽 경계는 데이터가 답한다.

```
소매 길이 차 = 0   →  정확히 손목
```

**진짜 미확정은 「밴드 폭」 하나뿐이다.** 차이 몇 cm까지를 「손목」으로 볼 것인가. 이건 인체 데이터가 아니라 **표현의 문제**라 사이즈코리아에 답이 없다 — Q1 과 성격이 다르다.

⚠️ **Q1 과 묶어서 결정하지 말 것.** Q1 은 데이터로 풀리고 Q2 는 합의로 푼다. 섞으면 「데이터로 정했다」는 말이 절반만 참이 된다.

참고로 손등 쪽 상한은 `손직선길이`(손 카테고리)로 근거를 댈 수 있다 — 「일부 덮음」이 손 길이의 몇 분의 일인지는 여전히 합의 사항이지만, 적어도 「손등을 다 덮는 길이」가 몇 cm인지는 데이터로 말할 수 있다.

**A3 구현 시 안전한 기본값** — 경계가 안 정해지면 `sleeveLabel` 을 **`null` 로 둔다.** 지금과 같은 상태라 아무것도 나빠지지 않는다. 기장(Q1)만 채우고 소매는 비워도 계약이 깨지지 않는다 (둘 다 선택 필드다).

### ✅ Q3 · A4 신체 치수 추정 계수의 근거 — 종결 (2026-08-20)

**1번 길로 갔다.** 사이즈코리아에서 직접 뽑아 왔다 — PRD가 지목한 바로 그 출처다.

**앵커: 제8차 한국인 인체치수조사 · 20~24세 평균** (sizekorea.kr 「인체 항목 검색」, 2026-08-20 조회. 표본 항목당 남 789~798명 · 여 714~716명)

| | 키 | 몸무게 | 가슴둘레 | 허리둘레 | 어깨너비 | 팔길이 |
|---|---|---|---|---|---|---|
| 남성 | 174.99 | 72.68kg | 101.04 | 82.06 | 40.01 | 59.06 |
| 여성 | 161.79 | 55.31kg | 88.17 | 72.62 | 34.70 | 54.10 |

**스케일 법칙** — 조사가 주는 것은 「평균·분위수」지 조건부 추정이 아니다. 그래서 평균을 앵커로 놓고 두 성질로 늘린다.

```
길이(어깨·팔)   ∝ 키
둘레(가슴·허리) ∝ √(몸무게 / 키)     ← 단면적 ≈ 부피/키, 둘레 ∝ √단면적
```

닮은꼴로 커지면(키 ×1.1 · 몸무게 ×1.331) 둘레도 ×1.1 이 되는 성질을 만족한다. 구현은 `fit/estimate.py`, 테스트 30건 + 돌연변이 14종 사살.

⚠️ **앵커는 실측이지만 스케일 법칙은 가정이다.** 이 구분을 문서에서 지우지 말 것. 특히 **허리**는 살이 먼저 붙는 부위라 실제로는 가슴보다 몸무게에 더 민감한데, 지수를 다르게 두려면 원시 데이터로 적합해야 한다. 눈대중으로 지수를 손대는 것이 더 나쁘므로 같은 식을 쓴다.

⚠️ **어깨너비의 정의가 옷과 정확히 같지 않다** — 조사값은 등을 따라 잰 체표 거리, 의류는 봉제선 사이 평면 거리다. 체표 쪽이 조금 길다. 가슴이 등급을 정하고 어깨는 보조 지표라 여기까지만 맞췄다.

⚠️ **앵커가 20대다.** 프로필이 나이를 안 받으므로 전 연령에 20대 평균을 쓴다. 키·몸무게로 조건화하면서 나이 효과가 상당 부분 흡수되지만(나이 들면 키가 줄고 몸무게가 는다) 완전하지는 않다. 나이를 받게 되면 앵커를 연령대별로 늘리면 된다 — 표는 같은 화면에서 뽑는다.

> 2번 길(추정을 빼고 실측 필수)은 안 갔다. 「키·몸무게만 넣어도 결과가 나온다」가 이 서비스의 진입 장벽을 낮추는 지점이라, 심사위원이 자기 가슴둘레를 몰라 막히는 쪽이 더 큰 손해였다.

### ✅ Q7 · 폰 사진의 EXIF 회전을 정규화하는가 — **한다. 구현 완료 (2026-08-19)**

`images/validate.py` 의 `normalize_photo()` 가 저장 전에 회전을 픽셀에 굽는다. 테스트 22건 — 아래 실측 그대로를 케이스로 넣었고, `exif_transpose` 한 줄을 지우면 테스트가 죽는다(돌연변이 확인). Pillow 는 의존성에 추가했다.

아래는 판단 근거로 남긴다.

피그마가 폰 화면 기준이라는 게 확인되면서([T6](#-t6--웹인가-앱인가--백엔드에는-영향-없음으로-종결)) 따라오는 문제다. **폰으로 찍은 세로 사진은 픽셀을 눕혀 저장하고 "90도 돌려서 봐라"라는 EXIF 태그를 따로 단다.** 브라우저와 사진 앱은 그 태그를 읽어 똑바로 보여주지만, `Image.open(f).size` 는 안 읽는다.

**실측했다.** 512×768 세로 사진을 만들어 EXIF orientation을 붙인 결과:

```
사용자가 보는 크기      : 512 x 768   (세로 사진)
naive .size 가 읽는 값  : 768 x 512   ← 가로세로가 뒤바뀐다
exif_transpose 적용 후  : 512 x 768
```

| 어디 | 증상 |
|---|---|
| **D2 해상도 검증** | `높이 >= 768` 이 실패한다 → **512×768 을 만족하는 멀쩡한 사진이 거부된다** |
| **이미지 생성** | 옆으로 누운 사람 사진이 그대로 모델에 넘어간다 |

둘 다 에러가 안 나고, 시연에서 **"왜 내 사진만 안 되지"** 로 나타난다. 그 자리에서 원인을 찾을 수 없다.

**해결은 한 줄이다.** 저장 전에 한 번 굽고, 그 뒤로는 아무도 EXIF를 신경 안 써도 되게 한다.

```python
from PIL import ImageOps
image = ImageOps.exif_transpose(image)   # 회전을 픽셀에 굽고 태그를 정리한다
```

⚠️ **Pillow가 아직 의존성에 없다.** D2가 해상도를 읽으려면 어차피 필요하니 그때 같이 추가하고 **팀에 알린다** ([CLAUDE.md 4절](../CLAUDE.md)).

D2가 20분짜리로 잡혀 있어 모르면 그냥 지나간다.

### ✅ T7 · 비밀번호 규칙 — PRD에 있었다 (2026-08-19 교정)

「PRD에 규칙이 없다」고 적었던 건 틀렸다. **PRD 7.8 에 있다: 「8자 이상. 영문·숫자·기호 중 2종 이상 조합」**, 7.1 에 「특수문자 강제 없음」. 2종 조합을 빠뜨리고 있어서 8/19 추가했다.

⚠️ 한글은 영문도 숫자도 아니라 **「기호」로 센다.** `isalnum()` 은 한글에 `True` 라 그대로 쓰면 한글+숫자 비밀번호가 1종으로 잘못 세어진다.

**최대는 규칙이 아니라 라이브러리 한계다.** bcrypt는 72바이트를 넘기면 **예외를 던진다**(조용히 자르지 않는다). 한글은 UTF-8 3바이트라 **24자면 이미 72바이트**다. 안 막으면 긴 한글 비밀번호를 넣은 사용자가 500을 본다.

```
"가" * 24  →  72바이트  (통과)
"가" * 25  →  75바이트  (400 PASSWORD_TOO_LONG)
```

바꾸려면 `api/auth.py` 의 `Password` 한 줄만 고친다.

한편 [피그마 `FitCheck_UI`](https://www.figma.com/design/vvdBh9c6tJyQb4PRx6CV8i/FitCheck_UI) 는 **전부 폰 크기 세로 프레임**이다 (섹션 구성은 plan.md와 정확히 일치 — 랜딩 / 로그인·가입 / 프로필 1·2단계 / 전신 사진 / 의류 등록 / 생성 대기 / 결과 / 내 피팅 / 사이즈 비교).

**둘을 합치면 「폰 화면 기준 모바일 웹」이 가장 앞뒤가 맞는다.** 네이티브 앱이라면 "브라우저 알림 권한"이나 "브라우저 세션 식별자"라는 말이 나올 수 없다. 다만 **폰 프레임만으로는 네이티브 앱과 모바일 웹이 구분되지 않는다** — 확인이 필요하다.

그런데 **어느 쪽이든 백엔드가 안 바뀐다.** 갈릴 수 있었던 네 군데를 실제로 보면:

| 갈릴 수 있었던 곳 | 왜 안 갈리나 |
|---|---|
| **CORS** | 웹이면 필요하고 앱이면 **브라우저가 없어 무시된다.** 있어도 해가 없으므로 앱이어도 아무것도 안 깨진다 |
| **인증 토큰** | 쿠키를 골랐으면 갈렸다 — SameSite·CSRF 대응이 백엔드 일이 됐을 것. **헤더 JWT라 둘 다 동일** |
| **F-11 알림** | Web Push(VAPID) vs FCM/APNs 는 완전히 다르다. **백엔드 발송분을 잘라서**(plan.md 8절) 차이가 사라졌다 |
| 사진 업로드 · 서명 URL · **그 외 모든 API** | 원래 동일. 백엔드는 프론트가 뭐로 그려지는지 모른다 |

⚠️ **무영향인 게 우연이 아니라 고른 결과다.** 누가 "쿠키 인증으로 바꾸자"거나 "Web Push 살리자"고 하면 그 순간 다시 갈린다. 그때 이 표를 다시 본다.

#### 대신 진짜 필요한 질문은 이것 하나였다

**프론트가 배포되는 origin이 무엇인가** (웹인 경우에만).
